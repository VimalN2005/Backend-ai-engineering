# Day 32: Django Setup, Project Architecture & Settings Modularization

Django is the gold standard of Python web frameworks—powering platforms like Instagram, Pinterest, Spotify, and Disq. Known as *"the web framework for perfectionists with deadlines,"* Django follows a **batteries-included** philosophy, providing an integrated ORM, authentication engine, security defenses, and database migration manager out of the box.

However, default scaffolding generated by `django-admin startproject` is designed for introductory tutorials, not enterprise production. Monolithic single-file `settings.py`, flat directory layouts, hardcoded secrets, and default User models cause severe architectural debt.

This deep dive establishes the **enterprise two-tier project layout, multi-environment settings modularization, environment variable validation, and production security hardening**.

---

## 1. Django's Architectural Philosophy & MTV Pattern

Django structures applications using the **Model-Template-View (MTV)** pattern, which maps directly to the classic Model-View-Controller (MVC) paradigm:

```
+-----------------------------------------------------------------------------------+
|                        DJANGO MTV vs CLASSIC MVC MAPPING                          |
+-----------------------------------------------------------------------------------+
| MTV Component  | MVC Equivalent | Responsibility                                  |
+----------------+----------------+-------------------------------------------------+
| Model          | Model          | Data access layer, DB schemas, ORM logic, ACID  |
| Template       | View           | Presentation layer (HTML, Jinja, DRF Serializers)|
| View           | Controller     | Business logic, HTTP handler, request/response  |
+----------------+----------------+-------------------------------------------------+
```

### Core Django Tenets:
1. **Batteries-Included**: Provides built-in authentication, ORM, CSRF protection, session management, and the Django Admin interface.
2. **Explicit is Better than Implicit**: Configuration over magic conventions; explicit URL routing, model field declarations, and middleware pipelines.
3. **DRY (Don't Repeat Yourself)**: Define database schemas once in Python models; Django automatically generates migrations, admin UIs, and serialization contracts.

## 2. Default vs Enterprise Two-Tier Project Layout

The default `django-admin startproject myproject` creates a flat, confusing structure where configuration files and app source code sit side-by-side with root repository files (Dockerfiles, READMEs, scripts).

### Production Two-Tier Layout:

```text
my_enterprise_repo/              <-- Repository Root (Git, CI/CD, Docker)
├── .env.example                 <-- Documented environment variables template
├── .gitignore                   <-- Ignored pycache, sqlite, media, local secrets
├── Dockerfile                   <-- Multi-stage production container build
├── docker-compose.yml           <-- Local dev orchestration (PostgreSQL, Redis)
├── pyproject.toml / poetry.lock <-- Dependency manifest & strict version pins
├── README.md                    <-- Project documentation & developer onboarding
├── scripts/                     <-- Deployment, entrypoint, & migration scripts
│   └── entrypoint.sh
└── src/                         <-- Django Project Root (PYTHONPATH root)
    ├── manage.py                <-- Django CLI entrypoint
    ├── config/                  <-- Project-wide configuration package
    │   ├── __init__.py
    │   ├── asgi.py              <-- Asynchronous ASGI entrypoint (Uvicorn)
    │   ├── wsgi.py              <-- Synchronous WSGI entrypoint (Gunicorn)
    │   ├── urls.py              <-- Root URL dispatcher
    │   └── settings/            <-- Split settings package
    │       ├── __init__.py
    │       ├── base.py          <-- Common configuration across all environments
    │       ├── development.py   <-- Local dev (DEBUG=True, local DB, debug toolbar)
    │       ├── production.py    <-- Production (DEBUG=False, strict SSL, S3, Sentry)
    │       └── testing.py       <-- Test suite (in-memory SQLite, fast hashers)
    └── apps/                    <-- Modular Pluggable Domain Applications
        ├── core/                <-- Abstract base models, utilities, pagination
        ├── users/               <-- Custom User model, auth backends, profiles
        ├── billing/             <-- Subscriptions, Stripe webhooks, invoices
        └── analytics/           <-- Telemetry, audit logging, reporting
```

### Benefits of the Two-Tier Layout:
- Keeps the repository root clean of Python package pollution.
- Setting `src/` as the working directory simplifies Docker builds and Gunicorn execution (`gunicorn config.wsgi:application`).
- Grouping domain apps inside `apps/` keeps top-level directories tidy when a project grows to 20+ apps.

## 3. Settings Modularization Pattern

A single monolithic `settings.py` creates massive bugs: developers accidentally commit `DEBUG = True` to production, or staging environments accidentally trigger production Stripe webhooks.

### The Split-Settings Architecture:

```
                           +----------------------+
                           |  settings/base.py    |
                           | (Common Config, ORM, |
                           |  Middleware, Auth)   |
                           +----------+-----------+
                                      |
            +-------------------------+-------------------------+
            |                         |                         |
            v                         v                         v
+-----------------------+ +-----------------------+ +-----------------------+
| settings/development  | |  settings/production  | |   settings/testing    |
| (DEBUG = True, SQLite,| | (DEBUG = False, S3,   | | (In-Memory DB, Fast   |
|  Debug Toolbar, CORS) | |  Strict HSTS, Sentry) | |  Hashers for Speed)   |
+-----------------------+ +-----------------------+ +-----------------------+
```

### 1. `config/settings/base.py` (Universal Settings)
Contains settings shared across all environments:
- Installed apps (`DJANGO_APPS`, `THIRD_PARTY_APPS`, `LOCAL_APPS`).
- Middleware stack order.
- Password validators.
- Internationalization (`TIME_ZONE = 'UTC'`, `USE_TZ = True`).
- Custom User Model declaration (`AUTH_USER_MODEL = 'users.User'`).

### 2. `config/settings/development.py` (Local Development)
```python
from .base import *

DEBUG = True
ALLOWED_HOSTS = ["localhost", "127.0.0.1", "0.0.0.0"]
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "dev.sqlite3",
    }
}
# Enable Django Debug Toolbar
INSTALLED_APPS += ["debug_toolbar"]
MIDDLEWARE.insert(0, "debug_toolbar.middleware.DebugToolbarMiddleware")
INTERNAL_IPS = ["127.0.0.1"]
```

### 3. `config/settings/production.py` (Production Security Hardening)
```python
from .base import *
import environ

env = environ.Env()

DEBUG = False
ALLOWED_HOSTS = env.list("DJANGO_ALLOWED_HOSTS")
SECRET_KEY = env("DJANGO_SECRET_KEY")

# Strict HTTPS & Cookie Security
SECURE_SSL_REDIRECT = True
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
SECURE_HSTS_SECONDS = 31536000  # 1 year
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_HSTS_PRELOAD = True
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")

# Production PostgreSQL with Connection Pooling
DATABASES = {"default": env.db("DATABASE_URL")}
DATABASES["default"]["CONN_MAX_AGE"] = env.int("CONN_MAX_AGE", default=60)
```

### 4. `config/settings/testing.py` (Lightning-Fast Test Runs)
```python
from .base import *

DEBUG = False
# Use in-memory SQLite for instantaneous test database creation
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": ":memory:",
    }
}
# Replace slow Argon2/PBKDF2 with MD5 for 10x faster unit test execution
PASSWORD_HASHERS = ["django.contrib.auth.hashers.MD5PasswordHasher"]
```

## 4. Environment Variable Management (The 12-Factor App)

According to the **Twelve-Factor App methodology (III. Config)**, code and configuration must be strictly separated. Sensitive configuration must be injected via OS environment variables.

### Why `python-environ` / `python-decouple` is Essential:
1. **Type Casting**: Environment variables are raw strings (`"True"`, `"60"`). `environ.Env.bool("DEBUG")` properly parses `"True"`, `"1"`, `"yes"` to `True`.
2. **Missing Variable Validation**: If a required production variable (like `DATABASE_URL` or `SECRET_KEY`) is missing, the application fails immediately at startup with an informative error rather than failing mid-request.
3. **Database URL Parsing**: Parses connection strings (`postgres://user:pass@host:5432/dbname`) directly into Django's nested `DATABASES` dictionary.

## 5. The Custom User Model Non-Negotiable Law

### The Golden Rule of Django Engineering:
> **Always configure a custom User model on Day 1 before running `python manage.py migrate` for the first time.**

If you migrate with Django's default `django.contrib.auth.models.User` and later decide to add a `company_id` field or allow email-only authentication, changing the user model requires manually editing historical database migration tables and rewriting foreign keys across all database tables—a notorious multi-day database migration nightmare.

### Minimal Custom User Model Setup:
In `apps/users/models.py`:
```python
from django.contrib.auth.models import AbstractUser
from django.db import models

class User(AbstractUser):
    """
    Enterprise custom User model.
    Inherits standard username, password, first_name, last_name, and permissions.
    Allows seamless future schema extensions without migration deadlocks.
    """
    email = models.EmailField(unique=True)
    is_verified = models.BooleanField(default=False)
```

In `config/settings/base.py`:
```python
AUTH_USER_MODEL = "users.User"
```

## 6. Modular Pluggable Apps Architecture

Django applications are self-contained, modular Python packages representing a specific business domain.

```
       [ apps/core ]        <-- Shared utilities, timestamps, base models
             ^
             |
       [ apps/users ]       <-- Authentication, RBAC, User profile
             ^
             |
       [ apps/billing ]     <-- Stripe payments, subscriptions, invoices
```

### App Separation Invariants:
1. **Single Responsibility Principle**: An app should handle one domain. Don't build a monolithic `main_app` containing users, blogs, and payments.
2. **Decoupled Imports**: If `billing` needs to react to user registration, use **Django Signals** or a **Service Layer function** rather than tight circular imports (`from apps.users.models import User` <-> `from apps.billing.models import Subscription`).
3. **App Registration Convention**: In `base.py`, separate `INSTALLED_APPS` into three explicit categories for readability:
   ```python
   DJANGO_APPS = [
       "django.contrib.admin",
       "django.contrib.auth",
       "django.contrib.contenttypes",
       "django.contrib.sessions",
       "django.contrib.messages",
       "django.contrib.staticfiles",
   ]
   THIRD_PARTY_APPS = [
       "rest_framework",
       "corsheaders",
   ]
   LOCAL_APPS = [
       "apps.core",
       "apps.users",
       "apps.billing",
   ]
   INSTALLED_APPS = DJANGO_APPS + THIRD_PARTY_APPS + LOCAL_APPS
   ```

## 7. Production Security Hardening Checklist

When preparing Django for production deployment (`DEBUG = False`):

```
+-----------------------------------+--------------------+------------------------------------------+
| Security Directive                | Production Value   | Threat Mitigated                         |
+-----------------------------------+--------------------+------------------------------------------+
| DEBUG                             | False              | Prevents stack trace / secret leakage    |
| SECRET_KEY                        | Injected from Env  | Prevents session hijacking & token forgery|
| ALLOWED_HOSTS                     | Explicit domains   | Prevents HTTP Host Header spoofing       |
| SECURE_SSL_REDIRECT               | True               | Forces HTTPS upgrade                     |
| SECURE_HSTS_SECONDS               | 31536000 (1 Year)  | Enforces Strict-Transport-Security (HSTS)|
| SESSION_COOKIE_SECURE             | True               | Cookies transmitted only over HTTPS      |
| CSRF_COOKIE_SECURE                | True               | CSRF tokens transmitted only over HTTPS  |
| SESSION_COOKIE_HTTPONLY           | True               | Blocks JavaScript access to session cookie|
| SECURE_BROWSER_XSS_FILTER         | True               | Activates browser XSS defense            |
| X_FRAME_OPTIONS                   | 'DENY'             | Prevents Clickjacking in iframes         |
| SECURE_CONTENT_TYPE_NOSNIFF       | True               | Prevents MIME-type sniffing attacks      |
+-----------------------------------+--------------------+------------------------------------------+
```

## 8. Database Connection Pooling (`CONN_MAX_AGE`)

By default, Django opens a brand-new TCP socket connection to PostgreSQL on every HTTP request and closes it at the end of the request (`CONN_MAX_AGE = 0`).
- At 500 req/sec, opening 500 TCP/TLS connections per second severely overloads PostgreSQL CPU and memory.
- **Production Standard**: Set `CONN_MAX_AGE = 60` (or higher) to keep database connections open across sequential requests on the same worker thread.
- For high-concurrency microservices, place **PgBouncer** in front of PostgreSQL with transaction-level pooling.

## 9. Structured Logging Configuration

Production Django services should never use raw `print()` statements. Configure Python's standard `logging` dictConfig to output structured JSON:

```python
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "verbose": {
            "format": "{levelname} {asctime} {module} {process:d} {thread:d} {message}",
            "style": "{",
        },
    },
    "handlers": {
        "console": {
            "class": "logging.StreamHandler",
            "formatter": "verbose",
        },
    },
    "root": {
        "handlers": ["console"],
        "level": "INFO",
    },
    "loggers": {
        "django.request": {
            "handlers": ["console"],
            "level": "ERROR",
            "propagate": False,
        },
    },
}
```

## 10. Django System Check Framework

Django includes a built-in verification engine that inspects models, settings, and database configurations for security flaws:
```bash
# Run production deployment security audit
python manage.py check --deploy --settings=config.settings.production
```
It flags missing security middleware, unencrypted cookies, and exposed secret keys before your Docker container ever launches into production traffic.

## 11. 7 Non-Negotiable Rules of Production Django Architecture

1. **Custom User Model on Day 1**: Always set `AUTH_USER_MODEL = 'users.User'` before the initial database migration.
2. **Never Commit Secrets to Git**: Inject `SECRET_KEY`, database credentials, and API keys exclusively via environment variables.
3. **DEBUG = False in Production**: Never deploy with `DEBUG = True`; it exposes internal database schemas and environment variables on unhandled exceptions.
4. **Split Settings Modules**: Never use a single monolithic `settings.py`. Split into `base.py`, `development.py`, `production.py`, and `testing.py`.
5. **Always Set `CONN_MAX_AGE`**: Enable persistent database connections in production to eliminate TCP handshake overhead to PostgreSQL.
6. **Separate Static from Media Files**: Static files belong on WhiteNoise or CDN; user-uploaded media files belong on object storage (AWS S3) with presigned URLs.
7. **Run `check --deploy` in CI/CD**: Automate Django's production security audit in GitHub Actions before deploying any build.

## 12. Architectural Settings Decision Matrix

| Setting Dimension | Development (`dev.py`) | Production (`prod.py`) | Testing (`test.py`) |
|---|---|---|---|
| **DEBUG** | `True` | `False` | `False` |
| **Database** | Local SQLite or Postgres | Managed PostgreSQL / RDS | In-Memory SQLite (`:memory:`) |
| **Password Hasher** | Standard PBKDF2 | Argon2 or PBKDF2 | Fast MD5 (Speed optimization) |
| **Email Backend** | Console (`ConsoleEmailBackend`)| SMTP / SendGrid / SES | In-Memory / Dummy |
| **Allowed Hosts** | `["*"]` or `["localhost"]` | Explicit Domain Names | `["testserver"]` |
| **HSTS / SSL Redirect**| Disabled | Strict 1-Year Preload | Disabled |
| **Connection Pooling** | `CONN_MAX_AGE = 0` | `CONN_MAX_AGE = 60+` | `CONN_MAX_AGE = 0` |
