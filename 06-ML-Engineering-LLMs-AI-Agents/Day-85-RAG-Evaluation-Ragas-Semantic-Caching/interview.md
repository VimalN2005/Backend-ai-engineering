# Day 85: Principal AI Systems Interview Questions — RAG Evaluation & Semantic Caching

### Q1: How do you mathematically define and implement the RAG Triad, and why are traditional NLP metrics like BLEU and ROUGE obsolete for modern RAG evaluation?
**Answer**:
- **Why BLEU/ROUGE Fail**: BLEU and ROUGE evaluate lexical precision and recall based on surface n-gram matches. They completely miss semantic equivalence (e.g. synonyms), are easily fooled by negation ("Server did not crash" vs "Server crashed" scores high ROUGE but has opposite meaning), and cannot evaluate whether an answer is grounded in retrieved documents.
- **The RAG Triad**:
  1. **Faithfulness**: $\frac{|\text{claims in } A \text{ entailed by } C|}{|\text{total claims in } A|}$. Evaluates whether the LLM hallucinated facts outside the retrieved context.
  2. **Answer Relevance**: $\frac{1}{N} \sum_{i=1}^N \cos(E(Q), E(q_i))$ where $q_i$ are reverse-generated queries from the answer. Measures whether the response directly addresses the user intent.
  3. **Context Precision**: Signal-to-noise ratio of the retrieval engine: $\frac{\sum_{k=1}^K \text{Precision@k} \times \text{rel}(k)}{\sum_{k=1}^K \text{rel}(k)}$. Penalizes distractor chunks ranked ahead of relevant chunks.
- **Production Implementation**: We decompose answers into atomic proposition claims, check entailment with a calibrated NLI model or structured LLM judge, and compute precision weighted across ranked chunks.

### Q2: What is the architectural lifecycle of an enterprise Two-Tier Semantic Response Cache, and how do you prevent cache drift and stampedes?
**Answer**:
- **Two-Tier Architecture**:
  - **Tier 1 (Exact Hash Cache)**: Uses SHA-256 over canonicalized query strings (whitespace collapsed, lowercase, punctuation stripped) in Redis/KeyDB. Yields $\mathcal{O}(1)$ lookups in $<0.2\text{ms}$.
  - **Tier 2 (Vector Semantic Cache)**: If Tier 1 misses, the query is embedded and scanned against a vector index (e.g. Milvus/Qdrant/Faiss) with cosine threshold $\tau \ge 0.90$.
- **Preventing Cache Drift**:
  - Semantic drift occurs when queries with subtly different intents match due to low thresholds (e.g. "Dev vs Prod"). We enforce $\tau \ge 0.90$ and combine vector similarity with hard metadata filters (user role, environment, organization ID).
- **Preventing Cache Stampedes (Thundering Herd)**:
  - We use **Probabilistic Early Expiration (XFetch)**:
    $$\Delta = -\beta \times \delta \times \ln(U)$$
    If $\text{TTL} - (\text{now} - \text{created}) < \Delta$, the first request initiates an asynchronous background refresh while continuing to serve the cached value to all incoming traffic, eliminating cache refresh thundering herds.

### Q3: How do you counteract LLM-as-a-Judge biases (Position Bias, Verbosity Bias, Self-Preference Bias)?
**Answer**:
- **Position Bias**: Models systematically prefer the first candidate evaluated.
  - *Mitigation*: We evaluate every pair twice with swapped ordering (`[A, B]` and `[B, A]`) and average the resulting scores or discard ties.
- **Verbosity Bias**: Judge LLMs consistently assign higher scores to longer, more elaborate answers even when factual density is lower.
  - *Mitigation*: Few-shot prompting with explicit negative examples of verbose fluff; penalizing answers exceeding concise word limits; calculating length-normalized evaluation metrics.
- **Self-Preference Bias**: Models (e.g. GPT-4) rate answers generated by their own family higher than answers from Anthropic Claude or Google Gemini.
  - *Mitigation*: Use cross-family judge ensembles (e.g. Gemini 1.5 Pro + Claude 3.5 Sonnet + GPT-4o) and report consensus scores; calibrate outputs against human golden datasets.

### Q4: When would you use Bi-Encoder similarity vs Cross-Encoder scoring in a Semantic Cache lookup?
**Answer**:
- **Bi-Encoder**: Encodes queries into fixed vectors offline/independently. Cosine similarity is computed via dot products in sub-millisecond time ($\mathcal{O}(1)$ per pair or $\mathcal{O}(\log N)$ via HNSW).
  - *Use Case*: High-throughput Tier 2 semantic caching where latency budget is $<5\text{ms}$.
- **Cross-Encoder**: Passes `(Query, Cached_Prompt)` jointly into full transformer self-attention layers, computing token-level interactions.
  - *Tradeoff*: High accuracy and zero loss of subtle context, but latency is 30–80ms per comparison.
  - *Production Pattern*: We use Bi-Encoder HNSW indexing to retrieve the top 3 semantic candidates, and if top similarity is in the ambiguous band $[0.88, 0.93]$, we run a lightweight MiniLM Cross-Encoder to make the final hit/miss decision.

### Q5: How do you handle real-time cache invalidation when underlying knowledge base documents change?
**Answer**:
- **Document-Level Version Tagging**: Every cached response stores the set of `document_ids` and `chunk_version_timestamps` that contributed to its generation.
- **Event-Driven Invalidation**:
  1. When a document is updated, the CMS/Ingestion worker publishes a Kafka/RabbitMQ event: `{"event": "DOC_UPDATED", "doc_id": "doc_123", "timestamp": 1718900000}`.
  2. Invalidation consumer flags all cached keys referencing `doc_123` as stale or purges them from the Redis inverted index `doc_to_cache_keys:doc_123`.
- **Namespace Eviction**: Staging environments or dynamic user workspaces are segmented into isolated namespaces, enabling atomic $\mathcal{O}(1)$ eviction of an entire department's cache upon permissions changes or data revisions.
