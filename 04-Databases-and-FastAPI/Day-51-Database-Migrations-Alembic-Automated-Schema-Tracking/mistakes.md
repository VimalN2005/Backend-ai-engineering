# Day 51: Critical Alembic Database Migration Antipatterns

This document explores the top 7 architectural mistakes engineers make when managing database schema migrations and automated schema tracking with **Alembic**. Each antipattern includes its underlying failure mechanism, bad code vs remediated code, and production rules.

---

## 1. Blindly Trusting Autogenerate on Column or Table Renames

### Failure Mechanism
SQLAlchemy reflection inspects database catalogs, but relational database catalogs do not provide history of intention. When an engineer renames a model attribute from `name` to `full_name`, Alembic compares the metadata against the live table and sees:
1. Column `name` is missing from the model $\implies$ generates `op.drop_column('users', 'name')`.
2. Column `full_name` is present in the model but not in the database $\implies$ generates `op.add_column('users', ...)`.

Running this in production **permanently deletes all customer data** stored in `name`!

### Bad Practice
```python
# Generated automatically by `alembic revision --autogenerate`
def upgrade() -> None:
    # CATASTROPHIC DATA LOSS: Drops existing name column and all data!
    op.drop_column('users', 'name')
    op.add_column('users', sa.Column('full_name', sa.String(length=150), nullable=True))
```

### Remediated Practice
```python
def upgrade() -> None:
    # 1. Inspect the autogenerated script before committing!
    # 2. Replace drop + add with an in-place column rename:
    op.alter_column('users', 'name', new_column_name='full_name')

def downgrade() -> None:
    op.alter_column('users', 'full_name', new_column_name='name')
```

## 2. Modifying Already-Merged / Applied Migration Files

### Failure Mechanism
A developer realizes they forgot an index in revision `2a3b4c` that has already been pushed to `main` and applied in staging or production. They open `2a3b4c_add_users.py`, add `op.create_index(...)`, and commit.

**The Fallout**:
- Databases that have already executed `2a3b4c` will never re-run it because their `alembic_version` table already marks `2a3b4c` as applied.
- The schema in production diverges from local development environments (silent schema drift).
- Team members pull `main` and experience checksum and DAG dependency inconsistencies.

### Bad Practice
```python
# Modifying an already-merged migration file to squeeze in an extra column
# versions/2a3b4c_add_users.py
def upgrade() -> None:
    op.create_table('users', ...)
    op.add_column('users', sa.Column('phone', sa.String(20))) # EDITED AFTER PUSH!
```

### Remediated Practice
```bash
# Rule: Migration files are IMMUTABLE once merged into shared branches!
# Always generate a forward migration to apply modifications:
alembic revision -m "add_phone_to_users"
```
```python
# versions/5d6e7f_add_phone_to_users.py
def upgrade() -> None:
    op.add_column('users', sa.Column('phone', sa.String(20), nullable=True))

def downgrade() -> None:
    op.drop_column('users', 'phone')
```

## 3. Creating Indexes on High-Traffic Tables Without `autocommit_block()`

### Failure Mechanism
In PostgreSQL, executing `CREATE INDEX` acquires a `SHARE` lock on the target table. On a table with millions of rows, building the index takes minutes, during which **all write operations (`INSERT`, `UPDATE`, `DELETE`) are completely blocked**!

To avoid table locks, PostgreSQL supports `CREATE INDEX CONCURRENTLY`. However, `CONCURRENTLY` cannot execute inside an explicit database transaction block (`BEGIN ... COMMIT`). If executed inside Alembic's default transaction, PostgreSQL aborts with:
```text
psycopg2.errors.ActiveSqlTransaction: CREATE INDEX CONCURRENTLY cannot run inside a transaction block
```

### Bad Practice
```python
def upgrade() -> None:
    # ACQUIRES EXCLUSIVE SHARE LOCK: Blocks all writes in production!
    op.create_index('ix_orders_customer_id', 'orders', ['customer_id'])
```

### Remediated Practice
```python
def upgrade() -> None:
    # Use autocommit_block() to exit Alembic's transaction context
    with op.get_context().autocommit_block():
        op.create_index(
            'ix_orders_customer_id',
            'orders',
            ['customer_id'],
            postgresql_concurrently=True, # Zero-lock concurrent index build
        )

def downgrade() -> None:
    with op.get_context().autocommit_block():
        op.drop_index(
            'ix_orders_customer_id',
            table_name='orders',
            postgresql_concurrently=True,
        )
```

## 4. Adding `NOT NULL` Columns to Populated Tables Without Defaults

### Failure Mechanism
Adding a column defined as `nullable=False` without providing a database `server_default` on a table with existing rows causes the database engine to immediately abort:
```text
sqlalchemy.exc.IntegrityError: Column 'status' contains null values / NOT NULL constraint failed
```

Furthermore, in older PostgreSQL or MySQL versions, adding a column with a default value triggered an immediate, full-table rewrite while holding an `ACCESS EXCLUSIVE` lock.

### Bad Practice
```python
def upgrade() -> None:
    # Fails immediately if 'orders' has any existing rows!
    op.add_column('orders', sa.Column('status', sa.String(30), nullable=False))
```

### Remediated Practice
```python
def upgrade() -> None:
    # 1. Add column with server_default (instant metadata-only operation in PostgreSQL 11+)
    op.add_column(
        'orders',
        sa.Column(
            'status',
            sa.String(30),
            server_default=sa.text("'PENDING'"),
            nullable=False,
        )
    )
```

If the default should only apply to existing rows and not future inserts:
```python
def upgrade() -> None:
    # Step A: Add nullable
    op.add_column('orders', sa.Column('status', sa.String(30), nullable=True))
    # Step B: Backfill existing rows
    op.execute("UPDATE orders SET status = 'PENDING' WHERE status IS NULL")
    # Step C: Alter to NOT NULL
    op.alter_column('orders', 'status', nullable=False)
```

## 5. Importing Application ORM Models Inside Migration Scripts

### Failure Mechanism
Developers often import their application's current SQLAlchemy models (e.g., `from myapp.models import User`) to query and transform rows during a data migration.

Six months later, an engineer deletes or renames a field on `User`. When CI runs migrations from scratch on a clean database, historical migration `0012` imports `User`, fails to find the deleted field, and crashes!

### Bad Practice
```python
# CATASTROPHIC ANTIPATTERN: Importing current application models
from myapp.models import User

def upgrade() -> None:
    bind = op.get_bind()
    session = sa.orm.Session(bind=bind)
    # Crashes in the future when User model changes!
    for user in session.query(User).all():
        user.normalized_email = user.email.lower()
    session.commit()
```

### Remediated Practice
```python
from sqlalchemy.sql import table, column
import sqlalchemy as sa

def upgrade() -> None:
    # Define an isolated, self-contained Core table representation
    users_table = table(
        'users',
        column('id', sa.Integer),
        column('email', sa.String),
        column('normalized_email', sa.String),
    )

    bind = op.get_bind()
    # Execute batch SQL update directly
    bind.execute(
        users_table.update().values(
            normalized_email=sa.func.lower(users_table.c.email)
        )
    )
```

## 6. Ignoring `compare_type=True` and `compare_server_default=True` in `env.py`

### Failure Mechanism
By default, Alembic's autogenerate detects added and dropped columns, but **completely ignores column type changes** (e.g., changing `String(50)` to `String(255)` or `Integer` to `BigInteger`) and **server default changes**.

Developers modify their models, run `alembic revision --autogenerate`, see an empty migration (`pass`), assume no changes were necessary, and deploy. In production, integers overflow when IDs exceed 2.14 billion!

### Bad Practice
```python
# alembic/env.py default configuration
context.configure(
    connection=connection,
    target_metadata=target_metadata,
    # compare_type defaults to False!
    # compare_server_default defaults to False!
)
```

### Remediated Practice
```python
# alembic/env.py
context.configure(
    connection=connection,
    target_metadata=target_metadata,
    compare_type=True,             # Detects type alterations (e.g. Integer -> BigInteger)
    compare_server_default=True,   # Detects server_default changes
)
```

## 7. Running Heavy Data Backfills Inside Transactional Schema DDL

### Failure Mechanism
Executing `UPDATE users SET full_name = ...` on a table with 20 million rows inside an Alembic migration holds row locks for minutes. This causes:
1. Massive transaction log (WAL) bloat.
2. Connection pool saturation as concurrent web requests queue waiting for locked rows.
3. Lock escalation leading to total service disruption.

### Bad Practice
```python
def upgrade() -> None:
    op.add_column('orders', sa.Column('uuid', sa.String(36)))
    # DANGEROUS: Millions of rows locked in a single monolithic transaction!
    op.execute("UPDATE orders SET uuid = gen_random_uuid()")
```

### Remediated Practice
```python
# Follow the Expand/Contract Pattern:
# Migration Step: Expand schema only (instant DDL)
def upgrade() -> None:
    op.add_column('orders', sa.Column('uuid', sa.String(36), nullable=True))

# Data Backfill: Executed OUTSIDE migrations via background worker in chunked batches
# e.g., Celery worker or standalone script:
#   UPDATE orders SET uuid = gen_random_uuid() WHERE id BETWEEN 1 AND 10000;
#   sleep(0.1);
```

*Following these remediations guarantees safe, zero-downtime, and predictable database evolutions.*
